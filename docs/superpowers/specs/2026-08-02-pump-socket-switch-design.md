## 1. 背景 · Background

老闆重新定義水泵節點的交付範圍：不再交付**完整抽水系統**，改為交付一個**220V 插座開關控制器**。現場自備水泵，插入我們的插座；我們負責偵測水位並決定何時通電。

The boss has re-scoped the pump node. We no longer deliver a complete pumping system; we deliver a **switched 220V socket**. The site plugs in its own pump. We own the sensing and the decision of when to energize it.

### 1.1 關鍵發現 · The finding that shapes this design

**韌體本來就已經在做這件事。** `control_logic.decide()` 是純函式安全核心，`pump_controller._apply_relay()` 只是把 GPIO 33 拉高或拉低——它從來不知道另一端接的是什麼。

The firmware already does this. `_apply_relay()` drives one GPIO; it has never known what is on the other side. **This is therefore an actuation-path and hardware-safety problem, not a control-logic rewrite.**

控制邏輯的改動被刻意壓到最小（見 §5.4）。大部分工作在市電側。

## 3. 架構：兩個正交軸 · Architecture: two orthogonal axes

本設計的核心是把兩件事拆開，且**互不參照**：

```
ACTUATOR_PROFILE  ──  GPIO 33 另一端是什麼 · what is on the other side
    "SOCKET_220V"  →  接觸器箱 + 現場自備水泵
    "PUMP_12V"     →  現有繼電器 + 12V 水泵（展示／備援）

PUMP_MODE         ──  水位代表什麼意義 · what the water means
    "DRAIN"        →  high_water 啟動水泵（現行行為）
    "COLLECT"      →  high_water 停止水泵 + CONTAINER_FULL
```

四種組合皆為合法部署：

| | `DRAIN` | `COLLECT` |
|---|---|---|
| **`SOCKET_220V`** | 淹水基坑，現場水泵 | 雨水收集，現場水泵 |
| **`PUMP_12V`** | 目前的台架節點 | 桌上展示收集情境 |

**Profile 攜帶**：安全時間參數、CT 啟用、HOA 啟用（見 §5.2）。
**Mode 攜帶**：`decide()` 中 Layer 4 的觸發分支，以及 `CONTAINER_FULL` 告警路徑。

兩者不互相讀取。

### 4.3 為何依 AC3 選型（本設計最容易犯錯之處）

繼電器與接觸器上印的電流值通常是 **AC1（電阻性負載）** 額定。水泵是 **AC3（感應電動機）**，啟動突入電流為運轉電流的 5–8 倍。經驗法則：AC3 約為 AC1 的 1/3 至 1/2。

| 標示 Marked | 實際馬達負載能力 Real motor duty |
|---|---|
| 「10A 250VAC」繼電器模組 | ≈3A ≈ 700W |
| 「20A」安裝型接觸器（AC1） | ≈7–10A AC3 ≈ 1,700–2,200W |
| 需求 Required | **≥10A AC3 ≈ 2,200W** |

> **採購規則**：看資料表的 **AC3 欄位**，不要看型號上的數字。「20A」安裝型接觸器很可能不足以承擔本設計宣告的最大負載。

### 4.4 保護接地 PE

- 箱內設 PE 端子排；PE 連續性：進線 → 插座 → 金屬箱體（若有）→ 電纜固定板。
- 水泵金屬外殼必須經插座 PE 接地。
- **RCD 不能取代接地**：沒有接地路徑時，RCD 只會在電流已經流經人體時才動作。
- 接地連續性測試列為驗收必要項目（§8.3）。

### 4.5 HOA 三段開關

標示為 **`AUTO / STOP / HAND`**，**不可標示為 "OFF"**。

> **STOP 不等於隔離。** HOA 開關控制的是**線圈**。接觸器一旦熔接，無論線圈是否激磁都維持導通。因此 STOP 位置**不保證插座無電**。隔離點為 MPCB，並在交接文件中明確指定為上鎖點（lockout point）。

**第二極接至 GPIO 13**：若無此訊號，技師每次切到 HAND 都會產生與「接點熔接」完全相同的電流特徵，導致誤發 CRITICAL 告警。

**上拉方向為關鍵**：依專案既有慣例，拉向 **非 HAND**。斷線時韌體判定為 AUTO，熔接偵測維持**啟用**（傾向誤報）。反向配置會使斷線永久停用熔接偵測（傾向漏報）。誤報優於盲點。

### 4.6 CT 前端

CT 輸出為**雙極性**。直接接進 ADC 腳位會只讀到半個波形，且負半週可能損傷腳位。

必要元件：
- 負擔電阻 burden resistor
- **1.65V 偏壓網路**（使波形落在 ADC 中段線性區）
- 箝位二極體

腳位為 **GPIO 39（ADC1_CH3，唯讀腳）**。
> 早期草案誤用 GPIO 35；該腳已於 `config.py:46` 保留給 `BATTERY_ADC_PIN`。

#### 4.6.1 二次側開路危害 · Open-secondary hazard 〔安全要求〕

**一次側帶電時，CT 二次側開路會使鐵芯飽和，於斷點產生數百伏至千伏級的高壓。** 這會擊穿前端電路，並對接觸者構成電擊危險。§7 已將「二次側開路」列為失效模式，但**僅就偵測面**（恆讀 0 → 誤報 `PUMP_NOT_RUNNING`）；此處補上安全面。

本設計採**外接負擔電阻**（非內建負擔的成品夾式模組），因此本危害為實際存在，非理論值。§4.8 採用 A 案（分艙）後，維修人員將例行性地在一次側帶電的情況下於低壓艙作業，此危害由「低機率焊接不良」升級為「常態暴露」。

**強制要求：**

1. **負擔電阻與 TVS／背對背齊納箝位，須直接永久焊接於 CT 二次線端**，不得置於任何可插拔連接器的另一側。
2. **任何維修用連接器必須位於負擔電阻的下游**（訊號側）。如此一來，維修時拔除接頭**不會**使二次側開路。
3. 低壓艙內 CT 線組須標示：**一次側帶電時不得斷開**。
4. §8.3 市電驗收須逐項確認上述三點（見該節查檢表）。

> 此要求不增加成本（兩個零件），但一旦箱體製作完成即無法補救——與 §4.8 A 案同屬「製作時近乎免費、事後無法加裝」的項目。

### 4.7 熱設計 · Thermal budget

本設計以「散熱困難」為由否決了 SSR 方案（§11 M-round-1），但密閉箱體內的損耗同樣可觀，必須一併計算：

| 元件 | 概估損耗 |
|---|---|
| 24V DIN SMPS | 3–5 W |
| 接觸器線圈（激磁時） | 2–5 W |
| ESP32（WiFi 運作中） | ≈0.5 W |
| MPCB / RCD（滿載時） | 1–2 W |
| **合計** | **≈ 10 W** |

台灣夏季機房環境溫度可達 40°C。密閉 IP54 箱體內部溫升 15–25°C 將使內部達 **55–65°C**。SMPS 與接觸器通常在 45–50°C 以上開始降額。

**要求**：
- 箱體選型須依實際損耗計算，不可僅依體積選擇。
- 優先採用金屬背板作為散熱面（不犧牲 IP 等級）。
- 若仍不足，改用附濾網通風孔並**明確記錄 IP 等級降低**。
- 驗收時量測箱內溫度（§8.3）。

### 4.8 維修性與服務通道 · Serviceability

> **ESP32 密封在市電箱內將無法重新燒錄。** 現行 4 台節點以實體 `mpremote` / `esptool` 更新；一旦進入本箱體，該流程即失效。緊急回復程序不可以是「在颱風中打開一個帶電的配電箱」。

**要求（三選一，實作計畫須明確指定）**：

| 方案 | 說明 |
|---|---|
| **A. 分艙設計（建議）** | ESP32 置於與市電艙分隔的低壓艙，低壓艙可在不隔離市電的情況下開啟 |
| B. 外部服務埠 | 經電纜固定頭引出 USB 至箱體外側（需維持 IP 等級） |
| C. OTA | 經 MQTT 進行簽章映像更新，含 A/B 回滾 |

**建議採 A + C**：實體分艙在製作時成本極低，事後無法加裝；OTA 則解決常態更新。

#### 4.8.1 決議（2026-08-02，使用者核可）· Decision

**採 A（分艙），現在做。C（OTA）明確延後，非放棄。B 否決。**

| | 理由 |
|---|---|
| **A 現在做** | 清單中**唯一**成本隨時間不對稱的選項：製作時約 NT$200–400，事後需重製箱體。其餘選項現在做與日後做價格相同。此處並非「選 A 而不選 C」，而是「選 A 以保留日後選 C 的能力」。 |
| **B 否決** | 戶外箱體經電纜固定頭引出 USB＝進水路徑＋腐蝕點；USB 連接器族本身無 IP 等級，密封蓋在第三次到場後就不會有人蓋回去。以維修便利換取市電箱體的進水風險，不成立。 |
| **C 延後** | 非單純增加一個任務。其一，MicroPython 在 ESP32 上的 A/B 回滾機制明顯弱於 ESP-IDF，等同自建回滾保證；OTA 失敗會留下一個接觸器狀態無人可觀測的節點。其二，本設計的安全論證建立在「運行中韌體＝台架已驗證的產出」之上，而 §8.3 要求簽署市電驗收紀錄、§8.4 要求組態管制——OTA 使韌體可在不經兩者的情況下改變，**因此 C 會反過來要求 §8.3／§8.4 重新開放**。以現行 4 台節點規模，到場更新比做錯這件事便宜。OTA 的效益門檻約在 20 台以上或現場確實無法到達時出現。 |

**A 案的三項強制建造條件**（缺一則分艙的宣稱不成立）：

1. **CT 負擔電阻與箝位須永久焊接於二次線端，維修連接器置於其下游**——見 §4.6.1。分艙使人員例行在一次側帶電時於低壓艙作業，此為 A 案引入的**新**風險，兩個零件即可消除。
2. **艙門偵測僅作遙測，不得作為互鎖。**「箱門開啟 → 抑制水泵」會製造出「微動開關腐蝕 → 淹水時水泵拒絕啟動」的新失效方向。告警可以，互鎖不行——與 `sensors.build_readers` 既有的「拉向未觸發位準」慣用法同一原則。
3. **SMPS 一次側留在市電艙。** 僅 24V 二次側、ESP32、CT 前端進入低壓艙；否則「不隔離市電即可開啟」的宣稱為假，而一個標示錯誤的分艙比沒有分艙更危險。

低壓艙門須標示：**開啟本艙門並未隔離市電**。

### 5.2 Profile 參數表 · Profile params

集中於單一表格，不散落成個別旗標：

| 參數 | `PUMP_12V` | `SOCKET_220V` | 理由 |
|---|---|---|---|
| `min_off_ms` | 0 | 180000 | `0` 表示 Layer 3.5 守衛不作用（12V 直流泵無此需求）。小型交流水泵每小時啟動次數上限約 10–20 次；180s ≈ 20 次/hr |
| `burst_cooldown_ms` | 30000 | 180000 | 衝突叢發（Layer 1）位於 min-off 之上，30s 會讓 AC 馬達在 15 分鐘內重啟約 30 次 |
| `boot_holdoff_ms` | 0 | 60000 | 一般開機保留，見 §5.6 |
| `boot_holdoff_urgent_ms` | 0 | 10000 | 高水位縮短條款（§5.6）。**僅 DRAIN 適用**——COLLECT 的高水位代表「容器已滿」，啟動水泵並非時效性動作 |
| `boot_loop_holdoff_ms` | 0 | 300000 | 確認重置迴圈時的延長保留；此情境下**不套用**高水位縮短條款——連續重啟的節點無法為其感測器讀值背書（§5.6） |
| `boot_loop_threshold` | — | 3 | 連續 3 次開機且中間未達健康門檻 → 判定重置迴圈（§5.6） |
| `boot_healthy_ms` | — | 300000 | 連續正常運作 5 分鐘後清除開機計數（§5.6） |
| `ct_enabled` | False | True | 同時作為「本節點為市電節點」的唯一標記——手動 ON 嚴格拒絕（§5.7）即以此為條件，不另設旗標以免兩者脫節 |
| `hoa_enabled` | False | True | |
| `wdt_required` | False | **True** | 220V profile 下 `WDT_ENABLED = False` 須以斷言擋下（§7） |
| `contactor_service_ops` | 0 | 60000 | 保養門檻，`0` 表示停用計數（12V 無接觸器）。暫定值為 10 萬次動作零件的 60%；採購定案後依實際 AC3 電氣壽命填入（§5.8、§10 項 5） |

> 三段式開機保留的優先順序（最嚴重優先）：重置迴圈 → 高水位緊急 → 一般。
> 判定邏輯集中於 `boot_guard.holdoff_total_ms()`，為純函數、可在桌面完整測試。

### 5.4 `control_logic.py` 變更

沿著真正的接縫拆分——**安全與模式無關，觸發才與模式有關**：

```
_safety_guards()      ← Layer 1,2,3,3.5  模式無關 mode-INDEPENDENT
   ├── decide()           ← Layer 4  DRAIN 觸發（維持現狀）
   └── decide_collect()   ← Layer 4  COLLECT 觸發（約 40 行，非 150 行）
```

如此 Mode C 不會讓「可能弄壞水泵」的程式面積加倍——已通過台架驗證的安全核心維持單一路徑。

**新增 Layer 3.5：min-off 防短循環守衛。**
使用**獨立**的 `min_off_elapsed_ms` 計時器，**不重用** `rest_elapsed_ms`。
> 重用會造成同一計時器有兩個消費者，且對 `None` 的解讀相反：Layer 3 以 `or 0` 強制為 0（阻擋），min-off 則視 `None` 為不阻擋。未來若有人修改該 `or 0`，min-off 行為會無聲改變。多一個整數換掉這個耦合是划算的。

**新增理由碼**：`MIN_OFF_WAIT`、`CONTAINER_FULL`、`COLLECT_RAIN_ON`、`SOURCE_DRY`。

**實作順序為強制要求**：
1. **Commit 1** — 純重構抽出 `_safety_guards()`，DRAIN 行為與現有測試**完全不變**且全綠。
2. **Commit 2** — 加入 `decide_collect()` 與 Layer 3.5。

> 混在一起提交時，COLLECT 的錯誤與重構的迴歸將無法區分。目前的安全核心已在 4 台節點上驗證運行。

### 5.5 CT 的角色 · What the CT does and does not do

**CT 不進入 `decide()`。** 它是輔助訊號與遙測，因此純安全核心保持不變，既有測試持續有效。

唯一例外是**過載跳脫**，那屬於**硬體保護**而非控制決策，位於 `decide()` 之上。

> **⚠ 實作約束（架構性）**：過載互鎖**必須**產生一個完整的 decision dict，經由 `pump_controller.apply()` 生效，**絕對不可直接操作繼電器**。
>
> 直接操作會使狀態機與實體致動器分歧：`ctrl_state["pump_state"]` 仍為 `ON`、`_on_since` 持續累計、下一輪 `decide()` 回傳 `HOLD`（維持現狀）而繼電器恰好已是 OFF，看起來正常但 Layer 3 的最大運轉計時器正在對一台沒有運轉的水泵累計，且因為沒有記錄到 ON→OFF 轉換，`rest_elapsed_ms` 永遠不會啟動。
>
> `apply_manual_override()` 已經正確採用此模式（回傳 decision dict 而非直接動作），照做即可。

### 5.6 重置迴圈與開機保留 · Reset loop and boot hold-off

**問題**：`_off_since` 位於 RAM（`pump_controller.py:19`）。WDT 重置迴圈（`WDT_TIMEOUT = 30000`）會讓 2200W 馬達每 30 秒重啟一次，完全繞過 min-off。

**不可行的做法 1**：把重置前的 tick 存入任何記憶體。`ticks_ms()` 重開機後從 0 重新計數，跨重置的差值無意義。NTP 牆鐘可行但需要網路，違反離線自主契約。

**不可行的做法 2（第二輪 A4 曾採用，第三輪 B2 推翻）**：把開機計數器存入 **RTC memory**。

> RTC memory 只在**軟體重置與深度睡眠**時保存，**電源重置與電壓驟降（brownout）重置會清空**。而颱風期間最可能的重置原因正是電壓驟降——市電不穩、水泵突入電流拉低電源軌。也就是說，此偵測器會在它唯一被設計要處理的情境中**失效為「無異常」**，且失效方向是危險側（保護消失，不是誤報）。

**採用做法**：開機計數器存放於 **NVS（flash）**，經 MicroPython `esp32.NVS` 存取。NVS 同時保存於電源重置與電壓驟降重置。

```python
from esp32 import NVS
nvs = NVS("sdprs")

# 開機時（僅一次）
try:
    n = nvs.get_i32("boot_count")
except OSError:          # key 不存在 → 首次開機
    n = 0
nvs.set_i32("boot_count", n + 1)
nvs.commit()
boot_loop = (n + 1) >= BOOT_LOOP_THRESHOLD   # → 延長開機保留 + 告警

# 確認本次開機健康後（連續正常運作達 BOOT_HEALTHY_MS，僅一次）
nvs.set_i32("boot_count", 0)
nvs.commit()
```

> `esp32.NVS.get_i32()` 在 key 不存在時**擲出 `OSError`**，不是回傳 `None`。首次開機必須走這條路徑，因此該 `try` 是正常流程而非例外處理。

短時間內連續開機且中間沒有一次成功長時間運轉，即為重置迴圈的特徵；偵測此特徵不需要跨重置的經過時間。

> **⚠ NVS 寫入壽命**：flash 抹寫次數有限（約 10⁵ 量級）。因此**只在開機時寫入一次**、**只在確認健康後清除一次**，不得每輪迴圈寫入。§5.8 的接觸器操作計數器有相同限制，兩者共用同一節流規則。

#### 5.6.1 未實作前的行為 · Behaviour before this lands

在 NVS 開機計數器實作之前，`SOCKET_220V` profile **不得部署**。單靠 RAM 的 `_off_since` 無法在重置迴圈中保護 2200W 馬達，而重置迴圈正是颱風情境的常見失效。此為 §12 的出貨前置條件。

**開機保留採分級制**：

| 情境 | 保留時間 |
|---|---|
| 冷開機、開機計數器無效 | 完整 `boot_holdoff_ms`（60s） |
| `high_water` 已觸發（DRAIN 模式的緊急情境） | 縮短至 10s |

> 單純套用 60 秒保留會造成：颱風期間節點因電壓驟降重置後，水位上升而水泵拒絕啟動 60 秒。防止短循環不能以犧牲主要使用情境為代價。

### 5.7 手動 ON 的拒絕條件擴充

`main.py:115` 目前僅在 `dry_run_protect` 或 `sensor_conflict` 時拒絕手動 ON，**未檢查 `max_runtime_rest`**。操作員在 Layer 3 冷卻期間點擊 ▶ 即可重啟一台剛連續運轉 10 分鐘的馬達。

12V 時無害；2200W 時這正是燒毀馬達的方式。

**變更**：在 `SOCKET_220V` profile 下，拒絕清單加入 `max_runtime_rest` 與 `min_off_wait`，並回傳剩餘秒數，讓儀表板能說明**為什麼**沒有動作。

### 5.8 接觸器操作計數與保養提示 · Contactor wear tracking

接觸器是本設計中**唯一會磨耗的零件**。其電氣壽命以**操作次數**計，而非年份——典型 AC3 電氣壽命約 10⁵–10⁶ 次。熔接（§7 第一列）通常是壽命終點的表現，而非隨機故障。

目前設計只能在**熔接發生後**偵測，屬事後偵測。加入操作計數即可在事前提示更換。

**做法**：沿用 §5.6 的 NVS，在每次 OFF→ON 轉換時遞增 `contactor_ops`，隨遙測發布。伺服器於超過門檻時發出 `CONTACTOR_SERVICE_DUE`（LOW，人工確認並於更換後歸零）。

| 參數 | 值 | 說明 |
|---|---|---|
| 提示門檻 | 依所選接觸器 AC3 電氣壽命的 **60%** | 採購定案後填入，不是任意數字 |
| 寫入時機 | 僅 OFF→ON 轉換 | 受 §5.6 的 NVS 壽命節流規則約束 |

> 以 `min_off_ms = 180s` 的最壞情況（每小時 20 次）估算，10⁵ 次約為 5,000 小時的連續密集切換；實際防災工作週期遠低於此，因此計數器的用途是**長期趨勢與交接紀錄**，不是短期告警。

## 7. 失效矩陣 · Failure matrix

| 失效 Failure | 偵測 Detected by | 回應 Response |
|---|---|---|
| 接觸器熔接 | CT：命令 OFF 但有電流 | `WELDED_CONTACT` CRITICAL，需人工確認 |
| 水泵未插／MPCB 跳脫／卡死 | CT：命令 ON 但無電流 | `PUMP_NOT_RUNNING` |
| **接觸器無法閉合**（線圈斷路、機械卡死） | 同上，**與上一列無法區分** | `PUMP_NOT_RUNNING`（診斷需人工到場） |
| 水泵堵轉 | CT：持續過電流 | 互鎖 OFF（經 `pump_controller.apply()`）+ `OVERLOAD_TRIP` |
| 乾轉 | 浮球（Layer 2 硬互鎖） | Layer 2 停泵。CT 低電流僅作為遙測佐證，**不參與該決策**（§5.5） |
| **CT 本身故障**（二次側開路） | 無法自我偵測 | 恆讀 0 → ON 時持續誤報 `PUMP_NOT_RUNNING`。**另有安全危害**：一次側帶電時開路將產生高壓，見 §4.6.1 之強制接線要求 |
| 操作員在面板操作 | GPIO 13 HOA 輔助接點 | 抑制熔接告警 + `HOA_LOCAL_CONTROL` |
| **XKC 卡在觸發狀態** | 無法自我偵測 | DRAIN：水泵持續運轉（受 Layer 3 上限約束）<br>COLLECT：水泵永不啟動 |
| ESP32 重置迴圈 | **NVS** 開機計數器（§5.6） | 分級開機保留 |
| **ESP32 當機且線圈維持激磁** | 內部 WDT（`WDT_TIMEOUT = 30000`）——**唯一防線** | 30s 內重置 → 線圈失電 → 水泵停止。見下方說明 |
| 接觸器累計操作接近壽命 | NVS 操作計數器（§5.8） | `CONTACTOR_SERVICE_DUE`，事前更換 |
| 市電中斷 | — | 節點失電 → 伺服器 `PUMP_OFFLINE_TIMEOUT` 判定離線（見 §9.1） |
| 網路中斷 | — | 依設計不影響控制 |

> **關於「ESP32 當機且線圈維持激磁」**：GPIO 33 在 MCU 當機時維持最後狀態，接觸器不會自行釋放，水泵將**持續運轉**。唯一使其停止的機制是 ESP32 內部看門狗（`WDT_ENABLED = True`，30 秒逾時）——重置使 GPIO 回到輸入態、MOSFET 關斷、線圈失電。
>
> **這代表最長非預期運轉時間為 30 秒**，可接受，但必須明確記錄：
> - `WDT_ENABLED` 在 `SOCKET_220V` profile 下**不得為 `False`**，實作時須以斷言強制。
> - 此防線**不涵蓋** MOSFET 短路或線圈接線短路等硬體失效；該類失效只能由 MPCB 過載或人工在 MPCB 上鎖處理（§4.5）。
> - 本設計**不採用**外部硬體看門狗。理由：內部 WDT 已涵蓋主要情境（韌體迴圈卡死），外部 WDT 增加的成本與失效點不成比例。此為明示的取捨，非疏漏。

#### 8.1.1 重構的驗證方法 · How the refactor is actually verified

§5.4 要求 Commit 1 為「行為不變的重構」，但**現有測試套件不足以證明這件事**——它涵蓋既有測試作者想到的情境，而重構的風險正在於未被想到的情境。「既有測試全綠」是必要條件，不是充分條件。

**強制程序**：在**動任何一行程式碼之前**，先產生黃金基準（golden fixture）。

```
1. 撰寫 test_decide_characterization.py，以決定性方式列舉輸入空間：
     readings × timing × ctrl_state 的組合網格
     （含邊界值：門檻上下、None、計時器剛好等於門檻）
2. 對 **重構前** 的 decide() 執行整份網格，把
     (action, next_state, flags, reason) 序列化為 JSON 存檔。
3. 該 JSON 隨 Commit 1 一起進版控，作為黃金基準。
4. 重構後重跑同一份網格，逐項比對。**任何一格不同即為迴歸。**
```

> 這份特徵化測試涵蓋的是「**目前的行為**」，包含目前的 bug。這是刻意的：重構的驗收標準是「不改變行為」，不是「行為正確」。行為的修正（例如 §5.7 的 `max_runtime_rest`）屬於 Commit 2 之後，且必須各自附上說明為何行為改變的測試。

**驗收條件**：
- Commit 1 — 黃金基準比對 100% 相同，且既有 DRAIN 測試全綠。
- Commit 2 — 黃金基準中 DRAIN 路徑仍 100% 相同；新增的 COLLECT 路徑另立基準。

## 9. 已知限制與假設 · Known limitations & assumptions

### 9.1 市電故障的可觀測性

v1 **不含**電池／UPS。`BATTERY_ADC_PIN` 與 `POWER_SOURCE_PIN` 目前皆為 `None`（`config.py:46-47`）。

市電中斷時節點失電，伺服器仍會經由 `PUMP_OFFLINE_TIMEOUT`（`config.py:28`）判定該節點離線——**故障不會完全無聲，但無法歸因**：「離線」可能是網路問題，也可能是市電問題。

24V 電源軌已預留容量，可於後續加裝 DIN DC-UPS 模組取得歸因能力。

### 9.2 未認證設備

本箱體為自行組裝的市電設備，**未取得 BSMI/CNS 認證**。

- 組裝與檢查應由合格電匠執行。
- 交接文件必須明載「本設備未經認證」。
- 需標示額定並註明「不得超載」。

### 9.3 無法量測突入電流

鉤表無法捕捉約 100ms 的突入尖峰；需示波器搭配電流探棒。若無此設備，**接觸器選型只能依賴資料表 AC3 額定**，這使 §4.3 的選型規則成為唯一防線。

### 9.4 感測器極性尚未驗證

`config.py:73-79` 明載 `FLOAT_ACTIVE_LOW` / `RAIN_ACTIVE_LOW` / `HIGH_WATER_ACTIVE_LOW` 為**推測預設值**，待 §A 台架極性驗證。該驗證**至今未執行**。

四種組態全部繼承此前提。**極性驗證是硬性前置條件，不是計畫中的一個步驟。**

### 9.5 RMS 取樣的即時性未驗證

每次輪詢阻塞約 60ms 進行 RMS 取樣，同時 MQTT 與 30s WDT 皆在運行。理論上可行，**但須實測後才可定案取樣率**。

### 9.6 插座專用性無法由系統強制

**假設**：該插座只接一台水泵。**沒有任何機制強制此假設。**

CT 量測的是插座的總電流，不是「水泵的電流」。若現場人員插入延長線再接其他設備：

| 情境 | 系統的解讀 | 實際情況 |
|---|---|---|
| 水泵故障，但插座上另接一台電暖器 | 「電流正常，運轉中」 | 水泵沒在抽水，且沒有告警 |
| 水泵正常，另接大功率設備 | 可能誤判 `OVERLOAD_TRIP` | 水泵正常 |
| 空載但有待機電流 | 熔接偵測門檻可能被跨越 | 誤發 CRITICAL |

**緩解（僅為程序性，非技術性）**：
- 插座面板標示「**專用插座——僅供水泵使用，不得外接延長線或其他設備**」。
- 列入 §8.4 驗收核對清單。
- 列入交接文件（§12.3）。

> 技術性強制需要在水泵端加裝獨立感測，超出「切換插座」的交付範圍。本項為**已接受的殘餘風險**，非待解問題。

### 9.7 插頭與轉接責任 · Plug and adapter responsibility

插座選用 **NEMA 6-15R（220V 專用防呆）**，其用意是讓 110V 設備**插不進去**（§11 C2）。

**此防呆可被一個 NT$50 的轉接頭完全繞過。** 轉接頭正是 110V 設備接上 220V 的途徑，而 220V 加在 110V 馬達上通常在數秒內冒煙。

**責任界線（須在交接文件明載）**：

| 項目 | 責任方 |
|---|---|
| 插座型式與額定標示 | **我方** |
| 水泵本體、其插頭、其電壓相容性 | **現場** |
| 任何轉接頭／延長線 | **現場**，且**明文不建議** |
| 水泵插頭改接為 NEMA 6-15P | 現場自行委請合格電匠 |

> 面板標示須同時寫明**電壓與最大功率**（例如「220V～ 10A 2200W MAX」），不能只寫「水泵專用」。使用者判斷相容性的依據就是這行字。

## 12. 交付範圍 · Delivery scope

**Phase 1（本規格）**：市電箱硬體 + `edge_pump` 韌體變更 + 台架驗收程序。

**Phase 2（排在 SPA lane 之後）**：遙測欄位、五種告警類型、儀表板顯示（§6）。

**不在範圍內 Out of scope**：電池／UPS（§9.1）、設備認證（§9.2）、現場水泵本身、插頭轉接（§9.7）。

### 12.1 12V 版本的交付內容 · What "keep the 12V version" actually means

決策 2（保留 12V 作為展示／備援）**純屬韌體範疇，無任何硬體工作**：

- 現有 12V 台架節點**不需改裝**，不進市電箱，不加 CT，不加 HOA。
- 交付物是 `ACTUATOR_PROFILE = "PUMP_12V"` 這個預設值，以及 §8.2 台架矩陣中涵蓋它的那兩格。
- 12V 節點**不繼承** `SOCKET_220V` 的安全參數（§5.2 已分列），也不受 §5.6.1 的出貨前置條件約束。

> 換言之：12V 版本的「維護成本」是測試矩陣從 1 種組態變成 4 種，不是第二套硬體。

### 12.2 現有節點的更新與回復 · Fleet update and rollback

現行 **4 台已驗收節點**執行的是目前的韌體。本規格的變更會觸及它們共用的 `control_logic.py`，因此更新策略是交付的一部分，不是實作細節。

**設計上的保障**：§5.1 的兩個新設定預設值即為現行行為（`PUMP_12V` / `DRAIN`），因此重新燒錄既有節點在行為上是**中性**的——這是刻意的，讓更新與行為變更兩件事分開發生。

| 步驟 | 內容 |
|---|---|
| 1. 標記已知良好版本 | 更新前對現行韌體打 git tag，作為回復目標 |
| 2. 金絲雀 | 先更新**一台**節點，觀察一個完整的乾濕循環後再推其餘 |
| 3. 其餘節點 | 逐台更新，非同時 |
| 4. 回復 | 以 `mpremote` 重新燒錄步驟 1 的 tag。**回復必須實測過一次**，未演練的回復程序不算回復程序 |

> **這仍是實體接觸更新**（`mpremote` / `esptool`），與 edge_glass 的 rsync 佈署不同，也與 §4.8 的 OTA 方案不同。OTA 若採用，將取代本節；在 OTA 落地前，本節即為程序。
